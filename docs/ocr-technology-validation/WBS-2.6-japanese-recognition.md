# WBS 2.6 日本語画像での認識確認

## 結論

WBS 2.5のブラウザPoCを用い、ローカル配置した`PP-OCRv5_mobile_det`と`PP-OCRv5_mobile_rec`で日本語画像を認識できた。入力した2行に対し、空白と改行を含めて次の結果を完全一致で取得した。

```text
日本語の文字認識
東京 2026
```

WBS 2.6の完了条件「日本語結果取得」を満たす。ただし、この試験は技術成立性の確認であり、実用画像に対する精度評価ではない。

## 試験条件

| 項目 | 条件 |
|---|---|
| 実施日 | 2026-08-06 |
| OS | Windows |
| ブラウザ | Microsoft Edge headless |
| 入力形式 | Canvasから生成したPNG |
| 画像サイズ | 1600×500 px |
| 背景・文字色 | 白（`#ffffff`）・黒（`#111111`） |
| フォント | `Yu Gothic UI` |
| 1行目 | `日本語の文字認識`、700、108 px |
| 2行目 | `東京 2026`、600、88 px |
| OCR言語設定 | `japan` |
| OCRモデル世代 | PP-OCRv5 |
| 推論backend | ONNX Runtime Web WASM |
| モデル・WASM | 同一オリジンのローカル資産 |

対象OSの標準環境という前提を曖昧にしないため、E2Eは画像生成前に`Yu Gothic UI`を利用可能であることも検証する。画像は試験実行時に生成し、生成物をリポジトリへ保存しない。

## 認識結果

| 行 | 入力 | 出力 | 判定 |
|---:|---|---|---|
| 1 | `日本語の文字認識` | `日本語の文字認識` | 完全一致 |
| 2 | `東京 2026` | `東京 2026` | 完全一致 |

ひらがな、カタカナ、漢字、英字、数字を含む1枚の画像から日本語結果を取得できた。E2Eは正規化された本文全体を`日本語の文字認識\n東京 2026`と完全一致で検証する。

## 自動検証

Playwright E2Eへ、日本語専用ケースを追加した。このケースは次を検証する。

- `Yu Gothic UI`が利用可能である。
- OCR状態が成功になる。
- 認識本文が期待する2行と完全一致する。
- 要求したruntime backendが`wasm`である。
- 外部オリジンへのリクエストが発生しない。
- 失敗したリクエストがない。
- ページ例外がない。

英数字ケースを含む最終実行では、E2E 2件が成功した。日本語ケースのテスト所要時間は7.8秒、全体は22.9秒だった。この時間にはページ操作や検証を含むため、純粋なOCR性能値としては扱わない。

## 変更範囲

- PoC画面のサンプルボタンを英数字用と日本語用に分離した。
- 1つの画像生成関数へ2行の文字列とフォントを明示的に渡す構成とした。
- OCRエンジン、モデル設定、結果正規化には変更を加えていない。
- React、HeroUI、Electron、Workerは導入していない。

## 制約と残余リスク

- 白地に大きな黒文字という良好な条件だけを試しており、スキャン文書、写真、低解像度、縦書き、ルビ、複雑なレイアウトの精度は未確認である。
- 1枚だけの成立確認であり、OCR精度の保証や統計的評価には使用できない。
- `Yu Gothic UI`以外の日本語フォントや、ユーザー画像に埋め込まれた字形は未確認である。
- 正規化結果にはpolygonとconfidenceが含まれるが、その意味、座標系、妥当性はWBS 2.7で確認する。
- メインスレッドで実行しており、UI応答性はWBS 2.8で確認する。
- ネットワークアダプター遮断試験はWBS 2.10で実施する。今回確認したのはE2E中の外部オリジン要求が0件であることまでである。
- CSPの`unsafe-eval`要件を含むWBS 2.5のセキュリティリスクは解消していない。

## Gate Aへの反映

Gate A条件のうち「日本語モデルが利用できる」について、Windows上のブラウザPoCで日本語と英数字の混在画像から期待結果を取得できたため、技術成立性を確認した。

これは日本語OCRの精度・性能が実用範囲内であるという判定ではなく、Electron、Worker、portable、完全オフラインを含むGate A全体の採用判断も引き続き保留する。

## 完了条件

WBS 2.6の完了条件「日本語結果取得」を満たす。
